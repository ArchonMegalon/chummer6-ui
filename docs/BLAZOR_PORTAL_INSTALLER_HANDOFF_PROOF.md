# Blazor Portal Installer Handoff Proof

## Purpose

This document defines the source-staged proof contract for browser-to-portal handoff from the promoted Chummer Online browser client.

The web client should behave like another Chummer desktop client in the browser, which includes clean exits to install/update/support surfaces when a browser workflow needs desktop help or account recovery.

## Source-Staged Scope

The staged handoff lane covers source alignment for these portal routes and surfaces:

- `/downloads/`
- `/downloads/releases.json`
- `/downloads/install/avalonia-linux-x64-installer`
- `/downloads/install/avalonia-win-x64-installer`
- `/downloads/install/blazor-desktop-linux-x64-installer`
- `/downloads/install/blazor-desktop-win-x64-installer`
- `/contact`
- `/help`
- `/status`
- `/blazor/home`
- `/blazor/app`
- `/blazor/workbench`
- `/blazor/`

## Required UX Contract

The Chummer Online browser lane must keep these ideas true:

- `/blazor/` resolves into Chummer Online and immediately opens the Character Roster workflow via `app?command=character_roster`, not a generic app shell or compatibility/proof route.
- `/app` is the clean public Chummer Online route, redirecting into the hosted Blazor app while preserving command query strings; `/blazor/app` remains the hosted app route and `/blazor/workbench` stays available only for explicit workbench/proof compatibility.
- Chummer Online remains the primary user workflow, not a preview page.
- Desktop install/download handoff remains same-origin through `Chummer.Portal`. The shelf root carries `data-download-panel="desktop-downloads"`, is labelled by `desktop-downloads-title`, and is described by `fallback-link` so the edge-specific fallback posture is associated with the whole downloads panel. The shelf has a Chummer Online handoff action marked with `data-download-action="open-chummer-app"` and pointing at `/app?command=character_roster` so users can return directly to the Character Roster workflow without waiting for installer proof, and the downloads shelf keeps keyboard focus rings and a reduced-motion guard for its handoff links. Published artifact rows live in a labelled `data-download-list="published-artifacts"` region with `aria-describedby="published-download-description"` explaining that published artifacts are direct raw downloads from the current release manifest. The shelf exposes manifest summary markers through `data-download-status`, `data-download-version`, and `data-download-artifact-summary`, plus a visible `data-download-count` summary. The raw manifest link carries `data-download-manifest-link` and an accessible `Open raw releases manifest JSON` label. Fallback guidance carries `data-download-fallback-guidance` so probes and support tooling can distinguish alternate-lane copy from artifact rows. Its empty state is explicitly marked with `data-download-empty="true"`. Published artifact rows keep the visible link on the actual artifact download so anonymous users can install without a login loop. Route probes assert the rendered rows expose `data-download-action`, `data-download-install-route`, `data-download-raw-url`, `data-download-link-mode="raw-url"`, `data-download-platform`, `data-download-platform-label`, visible `direct download` text, and an `aria-label` marker. They preserve the raw manifest URL in `data-download-raw-url` and expose the matching install handoff route as metadata for installer-claim and support flows. Published rows also render the artifact id visibly, or `artifact id pending` when absent. Rows expose `data-download-link-mode="raw-url"` and visible `direct download` text so probes can confirm the user-facing link is not a login-gated handoff wrapper. The direct artifact link also carries an `aria-label` that includes the artifact label, platform, and direct-download wording.
- Blazor desktop compatibility installer routes remain visible in the same handoff contract even when Avalonia is the promoted native head.
- `/downloads/` includes a self-host operator lane marked with `data-self-host-downloads-panel="docker-operator"`. It names `docker compose --profile portal up -d`, links the same-origin release manifest through `data-self-host-release-manifest`, links the browser fallback through `data-self-host-browser-app` to the clean `/app?command=character_roster` Chummer Online Character Roster deep link, and tells operators to mount `releases.json` and the sibling `RELEASE_CHANNEL.generated.json` into the downloads volume before claiming installer availability. This is guidance only; proof-required installer routes stay proof-required until artifact bytes and startup proof exist.
- `/status` must state current release availability.
- The local OpenAPI contract at `/openapi/v1.json` must list `/app`, `/blazor/app`, `/blazor/home`, `/blazor/`, `/downloads/`, `/downloads/releases.json`, and `/downloads/install/{artifactId}` so self-host operators can discover the clean public Chummer Online route, hosted app path, orientation page, downloads shelf, manifest, and proof-required install handoff routes from the same-origin `/docs/` explorer. The `/docs/` explorer root carries `data-docs-panel="operator-openapi-explorer"` and exposes a direct shortcut rail marked with `data-docs-shortcuts="operator-recovery"` plus `aria-describedby="docs-shortcuts-description"` and `data-docs-shortcuts-description` helper copy. The OpenAPI load-state line is marked with `data-docs-summary="openapi-load-state"`, `role="status"`, and `aria-live="polite"`. The rendered route collection is marked with `data-docs-endpoints="openapi-route-list"`, `role="list"`, and `aria-label="Documented portal routes"`, while generated route cards render with `data-docs-endpoint-card="openapi-route"`, `data-docs-endpoint-route`, `data-docs-endpoint-family`, `data-docs-endpoint-methods`, `data-docs-endpoint-summary`, and `role="listitem"`. Operator shortcuts are marked with `data-docs-action="open-chummer-app"` whose operator shortcut opens the roster-start `/app?command=character_roster`, `data-docs-action="open-chummer-home"` using the configured Blazor overview path, `data-docs-action="open-downloads"`, `data-docs-action="open-status"`, `data-docs-action="open-help"`, `data-docs-action="open-contact"`, and `data-docs-action="open-openapi-json"`, with reduced-motion handling for those shortcut controls. Its top-level description names Chummer Online route discovery so the local contract reads as an operator map, not only an API endpoint list.
- The local OpenAPI contract keeps visible route-family labels so operators can understand the browser route purpose without reading raw JSON.
- The same OpenAPI contract must list `/contact` and `/status` so installer/account recovery, support handoff, and release availability are discoverable from the same self-hosted docs surface as the downloads routes.
- `/help` must stay same-origin and link users back to Chummer Online, the Chummer Online overview route, downloads/installers, release status, support contact, and local docs. The page carries `data-portal-help-panel="handoff-guide"` and `data-portal-help-boundary="source-guidance-only"` to avoid treating navigation guidance as runtime proof.
- Local self-host receipt metadata must keep `/downloads/`, `/downloads/releases.json`, installer handoff routes, `/contact`, `/status`, and `/help` visible together so Docker refresh receipts can report the same portal-boundary breadth as the source-staged handoff contract.
- `/docs/docs.js` marks rendered downloads endpoints with `data-openapi-download-route="true"`, installer handoff endpoints with `data-openapi-installer-handoff-route="true"`, release status endpoints with `data-openapi-release-status-route="true"`, support handoff endpoints with `data-openapi-support-handoff-route="true"`, help handoff endpoints with `data-openapi-help-handoff-route="true"`, Chummer Online endpoints with `data-openapi-chummer-app-route="true"`, Chummer Online overview endpoints with `data-openapi-chummer-home-route="true"`, and hosted Blazor entry endpoints with `data-openapi-blazor-entry-route="true"` so support tooling can distinguish portal handoff routes from generic API endpoints without external CDN dependencies. It also renders visible `.route-family` labels such as `Chummer Online`, `Chummer Online overview`, and `Hosted browser entry`, plus `.endpoint-summary` operation copy, so operators can understand the browser route purpose without reading JSON. Route, family, summary, and method-label text are escaped through `escapeHtml` before insertion into the local explorer DOM.
- The portal root keeps Chummer Online route affordances visible with `data-portal-home-action="explore-chummer-online"` on the primary Character Roster CTA, `data-portal-home-route="chummer-app-roster"` for `/app?command=character_roster`, `data-portal-home-route="chummer-app"` for `/app`, `data-portal-home-route="chummer-home"`, and `data-portal-home-route="downloads"` so self-host users can open the Character Roster directly, choose the app shell, orientation page, or desktop downloads without knowing proof-route language.
- The portal source keeps those public browser route values centralized through `PortalRoutes.PublicApp`, `PortalRoutes.PublicAppSlash`, `PortalRoutes.PublicAppRoster`, `PortalRoutes.CharacterRosterCommand`, `PortalRoutes.BlazorApp`, `PortalRoutes.BlazorHome`, `PortalRoutes.BlazorAppSegment`, and `PortalRoutes.BlazorHomeSegment`, with `PublicAppRoster` derived from the command constant plus `BuildBlazorAppUrl` and `BuildBlazorHomeUrl` used for hosted route links, so generated links and the local OpenAPI explorer do not drift back into repeated route literals.
- The portal root hero is product-first, `Explore Chummer Online, downloads, and support from one self-hosted edge.`, and the route rail is labelled with `aria-label="Chummer Online routes"` so the `Open Character Roster`, `Open Chummer Online`, `Open Chummer Online overview`, and `Get desktop client` choices are exposed as one navigation group, with explicit hover/focus affordances and reduced-motion handling matching the recovery rails.
- Portal route probes and Playwright checks must treat `a.cta[href="/app?command=character_roster"][data-portal-home-action="explore-chummer-online"]` as the primary portal CTA, not `/blazor/app`, so the public edge opens the roster-first Chummer Online workflow before exposing implementation routes.
- Portal root, downloads, contact, help, status, and docs pages use the same polished Chummer Online slate/amber/mint/blue visual language as the Blazor client, including `--portal-gold: #ffd46f`, `--portal-mint: #8ff0bc`, `--portal-line: rgba(255,212,111,.25)`, blue accent gradients, restrained ambient glow, warm gold primary CTAs, and deep ink/surface contrast, so installer/support recovery feels like part of the same web desktop client rather than a separate default portal with a shared ambient grid texture, mobile-softened grid density, high-contrast portal action affordances, and reduced-motion-safe portal panel reveal. Downloads action pills, download route rows, docs shortcut pills, and OpenAPI endpoint cards keep matching hover/focus affordances with reduced-motion guards.
- Help, contact, and status recovery exits render as labelled navigation rails, `aria-label="Help recovery actions"`, `aria-label="Contact recovery actions"`, and `aria-label="Status recovery actions"`, with the same pill-style keyboard-focus treatment used by downloads and docs shortcuts instead of plain separator text. Help cards and the help/contact/status rails keep explicit hover/focus affordances and reduced-motion guards.
- Known compatibility routes without promoted artifact bytes return users to `/downloads/` with `installState=proof_required` instead of pretending the installer is published. The downloads shelf renders known compatibility handoff routes from release metadata, including their install posture. The compatibility list is a labelled region with `data-install-route-list="compatibility-handoff"` and `.compatibility routes` styling, a visible `data-install-route-count` summary, and an `aria-describedby` link to `compatibility-handoff-description` so probes and assistive technology can distinguish it from published artifacts. Route probes assert that compatibility description relationship as well. Its empty state is explicitly marked with `data-install-route-empty="true"`. It also shows promotion state so proof-required compatibility routes explain why they are not installable yet. Rows also show artifact availability, using an explicit `artifact pending` marker when release metadata has no artifact id. The visible posture, promotion, and artifact text carries stable `data-install-route-posture-label`, `data-install-route-promotion-label`, and `data-install-route-artifact-label` markers for support/probe tooling. Each listed compatibility route links back into its guarded installer route so users can reach the proof-required handoff flow deliberately, and the link carries an `aria-label` naming the proof-required installer handoff. Rows also expose the guarded route through `data-install-route-public-route`, `data-install-route-link-mode="proof-required"`, and visible `proof-required handoff` text so support/probe flows can distinguish guarded compatibility links from raw artifact downloads. Route probes assert those proof-required public-route, link-mode, and visible-label markers alongside the direct-download markers. It filters that list to proof-required or proof-capture fallback routes that are not already represented by published artifacts, including routes whose install posture is `proof_required` even when promotion state is absent. The downloads shelf renders that state as visible installer-proof guidance tied to the requested URL-encoded `next` route, and the guidance panel carries `data-install-next-route`, falling back to `requested-installer-route` when no next route is supplied, plus `role="status"` and `aria-live="polite"`. Route probes request the encoded `${baseUrl}/downloads/?next=%2Fdownloads%2Finstall%2Fblazor-desktop-linux-x64-installer&installState=proof_required` URL and assert the decoded rendered next-route value plus those live/status markers when requesting the proof-required downloads URL directly. Route probes decode the redirect `Location` header before asserting the preserved route and `installState=proof_required`. They also request the proof-required downloads URL directly and assert the visible guidance panel plus Chummer Online recovery action. It also provides an `Explore Chummer Online instead` recovery action back to the promoted web client's Character Roster workflow. The action uses the configured `CHUMMER_PORTAL_BLAZOR_URL` path plus `command=character_roster` rather than a hardcoded host.
- Installer claim routes may require login, but must preserve the intended next URL.
- `/downloads/` must explain current platform posture honestly.
- `/status` must state current release availability from the same `releases.json` manifest used by `/downloads/`. The page carries `data-portal-status-panel="release-availability"`, release status/version/artifact/install-route counters, a `data-portal-status-boundary="source-manifest-backed"` boundary marker, and actions back to downloads, Chummer Online, the Chummer Online overview route, help, and docs.
- `/contact` must route users into support without leaving the product shape. The self-host fallback page carries `data-portal-contact-panel="support-handoff"`, scenario markers for installer proof, account recovery, and Chummer Online support, plus actions back to Chummer Online, the Chummer Online overview route, `/status`, `/downloads/`, `/help`, and `/docs/`.

## Documentation Index Requirement

This contract must remain discoverable from `docs/BLAZOR_WEB_CLIENT_DOCS_INDEX.md` under the portal installer handoff section. It is adjacent to the Chummer Online and /blazor/workbench compatibility route source-staged proof set, but it must not be treated as a browser-workflow receipt or runtime installer proof.

## Boundary

This proof is source-only. It confirms route expectations are present in scripts and docs, but it does not prove the portal is running or that installer routes work at runtime.

Runtime claims still require the local portal proof and hosted public-edge proof receipts.
