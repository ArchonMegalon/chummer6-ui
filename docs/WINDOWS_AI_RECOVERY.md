# Gated Windows AI completion recovery

The action remains default-off. Operator qualification additionally requires a linked account and the current owner authority; linking alone does not enable an unqualified feature. Loading, reviewing and applying retain the original character and owner. Changed or cancelled context discards the result and closes an open review.

The pinned Core exposes separate creation-domain operations, not a unified atomic draft-completion operation. This correction therefore stops on the first failed or uncertain domain. It does not promise rollback, automatic resumption or complete AI finishing. Existing successful stages remain saved. The review explains this before confirmation.

Before dispatch, the app exclusively creates a private per-owner/per-character run record and flushes the frozen plan and operation identity. Each stage records dispatch before entering its Core-owned Load/Preview/Confirm path. Only observed results are recorded as confirmed. A duplicate invocation, changed plan identity or new process cannot replace that record and resend the operation. A malformed or interrupted record blocks writes. No credentials or account grant tokens are stored.

Reopening the action with fresh authorization loads the current character read-only and displays the retained historical outcomes. An unobserved result stays uncertain; loading a matching-looking character is not presented as an operation receipt. Pending records survive account transitions and can be inspected after returning with fresh authority. Do not clear the record to make a retry possible. Manual character inspection remains available.

This is bounded safety and recovery visibility for the gated implementation. Releasing AI Finish still requires the agreed all-archetype behavior and Core-owned atomic completion or qualified durable staged resumption, including exact receipt reconciliation, interruption/account-transition tests, and native review/apply/save/new-process recovery. No normal-user availability or complete AI acceptance is claimed here.

Validation retained with this correction: 15 focused headless/interaction cases pass. A separate console smoke test loads the compiled production run-store assembly, exits a process after a synthetic committed side effect but before observing its result, then starts a new process and verifies the original pending identity and zero replay dispatches. This is real process interruption with synthetic data, not a native Windows/Core character-save journey.
